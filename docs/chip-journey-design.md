# Chip Journey — מסמך תכנון: ISA, ארכיטקטורה וטכנולוגיות

## 1. מטרת הפרויקט
פלטפורמת למידה אינטראקטיבית שבה בונים מעבד שלב אחר שלב — משערים לוגיים ועד CPU עם פייפליין וקאש — עם ויזואליזציה בכל שלב. מטרת-על: העמקה חוויתית בארכיטקטורת מחשבים, כהכנה לתחום שבו עוסקת Qualcomm.

---

## 2. ה-ISA המינימלי (Instruction Set Architecture)

### פרמטרים בסיסיים
| פרמטר | ערך | הערה |
|---|---|---|
| רוחב מילה | 8 סיביות | מספיק לדוגמאות, קל לדבג ולהציג ויזואלית |
| מספר רגיסטרים | 4 (R0–R3) | R0 יכול להיות "always zero" מוסכם, כמו ב-MIPS |
| מרחב זיכרון | 256 בתים | נגיש דרך LOAD/STORE |
| דגלים (Flags) | Zero, Carry | לתמיכה ב-JZ ובחיבור עם carry |

### סט ההוראות (מינימלי אך Turing-complete בפועל)
| הוראה | קידוד (רעיוני) | פעולה |
|---|---|---|
| `ADD Rd, Rs1, Rs2` | opcode 0001 | `Rd = Rs1 + Rs2` |
| `SUB Rd, Rs1, Rs2` | opcode 0010 | `Rd = Rs1 - Rs2` |
| `LOAD Rd, [addr]` | opcode 0011 | `Rd = MEM[addr]` |
| `STORE Rs, [addr]` | opcode 0100 | `MEM[addr] = Rs` |
| `JUMP addr` | opcode 0101 | `PC = addr` |
| `JZ Rs, addr` | opcode 0110 | אם `Rs == 0` אז `PC = addr` |
| `HALT` | opcode 1111 | עצירת הריצה |

**החלטה פתוחה (לדון):** קידוד קבוע-אורך (כל הוראה 8 סיביות, opcode + 2 שדות רגיסטר) לעומת קידוד משתנה. מומלץ להתחיל בקבוע-אורך — פשוט יותר לדקד ולהציג.

### תוכנית בדיקה לדוגמה (לוודא שה-ISA מספיק)
תוכנית שמחשבת סכום 1..N ושומרת בזיכרון — דורשת לולאה (JZ+JUMP), חשבון (ADD), וגישה לזיכרון (LOAD/STORE). אם ה-ISA הזה מצליח לבטא אותה, הוא מספיק לשלב 1.

## 3. שלבי הפרויקט (Milestones)

1. **שערים לוגיים** — AND/OR/NOT/XOR כרכיבים בסיסיים, ויזואליזציה 2D, אינטראקציה (קליק = היפוך קלט)
2. **ALU** — בונים חיבור (half/full adder משערים), השוואה, מולטיפלקסור — הכל מהשערים משלב 1
3. **רגיסטרים וזיכרון** — flip-flops, register file, זיכרון פשוט (מערך)
4. **CPU חד-מחזורי** — fetch-decode-execute-writeback רץ ברצף, מריץ תוכנית אמיתית לפי ה-ISA שלמעלה
5. **Pipeline** — פיצול ל-5 שלבים, זיהוי hazards, stalls מוצגים ויזואלית
6. **קאש (בונוס)** — L1 cache פשוט, hit/miss מוצג גרפית
7. **תצוגת 3D סופית** — showcase view לכל המערכת שנבנתה

כל שלב = milestone עצמאי עם unit tests לפני חיבור ל-UI.

## 4. ארכיטקטורת תוכנה

```
chip-journey/
├── core/               # מנוע הסימולציה — TypeScript טהור, ללא תלות ב-UI
│   ├── gates.ts        # AND/OR/NOT/XOR + evaluate()
│   ├── circuit.ts      # גרף חיבורים בין רכיבים
│   ├── alu.ts          # שלב 2
│   ├── cpu.ts          # שלב 4 — fetch/decode/execute
│   ├── pipeline.ts     # שלב 5
│   └── __tests__/      # unit tests לכל מודול, לפני חיבור ל-UI
├── viz-2d/             # React + SVG — תצוגת הלמידה של כל שלב
├── viz-3d/             # Three.js (ES modules + importmap) — showcase סופי
└── tutor/              # (עתידי) שכבת AI שמסבירה מצב בזמן אמת
```

**עיקרון מנחה:** ה-`core` לא יודע שקיים UI בכלל. כל הלוגיקה נבדקת ב-unit tests נטו, וה-viz שכבות רק *קוראות* את המצב שלו ומציגות. זה גם מאפשר בעתיד להחליף את ה-`core` ב-Rust→WASM בלי לגעת בשכבות התצוגה.

## 5. החלטות טכנולוגיה

| שכבה | טכנולוגיה | נימוק |
|---|---|---|
| מנוע סימולציה (שלבים 1–4) | TypeScript | לולאת פיתוח מהירה, אין צורך בביצועים גבוהים עדיין |
| מנוע סימולציה (שלב 5+, אם נדרש) | הגירה ל-Rust→WASM | רק אם נתקלים בבעיית ביצועים אמיתית עם הרבה שערים/מחזורים |
| תצוגת למידה (שלבים 1–6) | React + SVG | קריאות לימודית גבוהה, פשוט לחבר לקליקים ואינטראקציה |
| תצוגת showcase סופית | Three.js — ES modules + importmap (**לא** global script ל-OrbitControls) | ראינו בפועל שזו הדרך התקינה כיום |
| בדיקות | Vitest / Jest על ה-`core` | core טהור = קל לבדוק בלי mocking של UI |
| (עתידי, אופציונלי) | MCP server שחושף את מצב הסימולטור | מאפשר "לשאול" על מצב הפייפליין ולקבל הסבר מבוסס state אמיתי |
| (עתידי, אופציונלי) | Claude API כ"מדריך" | הסבר טבעי בשפה חופשית על מה קורה בכל מחזור שעון |
